# Design

## Context

动机与范围见 [proposal.md](proposal.md)，行为约束见 [spec.md](specs/expired-link-replacement/spec.md)。

`AddTask` 只按同一 URL 找停止任务补填请求头；fetch 使用强 ETag 或 Last-Modified 处理原地址续传，但跨地址不具备资源身份保证。`partMeta` 当前保存 URL/验证器/长度，响应改名可能在没有部分数据时改路径。

实施顺序：无硬依赖；建议在多连接分片前实施，再由分片 change 扩展部分数据迁移。

## Goals / Non-Goals

**Goals:** 在现有包边界内实现上述行为，后台工作可取消、可用替身测试；保留旧数据读取与用户现有默认行为。

**Non-Goals:** 自动刷新签名 URL、抓取网页链接、跨域资源身份推断和更新正在运行的任务。

## Decisions

### 1. 状态与职责

新增按任务 ID 的 UpdateSource 工作流，先锁内校验 paused/failed 且 !working，登记编辑 generation，然后在锁外使用新请求选项探测；提交前重验任务状态、generation 及目标去重。网络失败、取消、状态冲突都不修改原地址与部分文件。

### 2. 核心执行方式

只对同源且 path 完全相同的查询参数更新考虑沿用数据；要求旧强 ETag、已知长度与新 206 Range 一致，最终重定向不得离开同一资源标识。不同查询也可能选择不同资源，故验证阶段以新地址和 If-Range 读取完整已有前缀，与本地文件逐块比较；全部相同才允许复用，后续继续仍对新地址校验相同强 ETag。比较使用任务/全局限速、代理、取消和停滞保护，不占管理器锁；无部分数据则跳过比较。不同源/路径、弱验证器或不相同前缀均从零开始。

### 3. 一致性与边界

验证成功产生 pending source revision：保留当前文件直到用户确认继续。若须重下，写入可恢复的 reset 标记/新源元信息后再截断，重启看到待重置标记必须从零，避免更新 URL 后崩溃又沿用旧数据。元信息采用临时文件+替换；不可在 Manager.mu 下做探测或磁盘 I/O。

### 4. 生命周期与交互

目标路径与文件名锁定为现有值，禁止后续 Content-Disposition 再更名；其他配置、队列序号、计划、任务限速、摘要保持。更新默认不继续，保持暂停；用户继续才走统一调度。

### 5. 集成与验证

清除旧 user/pass/headers，接受新输入经 ParseHeaders 和 requestClient 检查。用户可在同次操作明确重新填写，但不得隐式迁移旧认证；内存以外仍只写 HeadersRequired。错误不包含完整新旧 URL 或头值。

## Risks / Trade-offs

- 路径变化的相同文件不能复用旧进度 → 保守从头下载，明确说明该限制，避免错误续传。
- 前缀验证产生额外网络流量 → UI 显示验证中且可取消；说明此步骤保证安全复用而不保证节省已下载前缀的传输成本。
- 磁盘失败造成记录与部分内容不一致 → 持久 pending/reset 标记、幂等恢复和故障注入测试。

## Migration Plan

新增源修订/待重置字段缺失时按原下载方式处理。回滚前先完成或取消待更新操作并备份任务记录；不得让旧版本处理未完成的源切换事务。

先执行针对性用例，再执行全量测试与 MyGo 静态检查；界面变化检查两套主题、960×640 和 125% 缩放。平台服务以 deps 替身测试，原生行为另记真实验证范围。发布后更新 README 与 roadmap；本提案阶段不变更应用版本。
