# Design

## Context

动机与范围见 [proposal.md](proposal.md)，行为约束见 [spec.md](specs/per-task-rate-limits/spec.md)。

现有 bandwidth 在 `limit.go` 中以小 token bucket 全局共享，fetch 每次读取前 take、短读后 refund，停滞计时仅包围网络 Read。`limit_test.go` 已覆盖动态调整和取消。本设计扩展两级额度，不引入第二套传输代码。

实施顺序：无硬依赖；在多连接分片前实施，所有分片共享同一任务额度。

## Goals / Non-Goals

**Goals:** 在现有包边界内实现上述行为，后台工作可取消、可用替身测试；保留旧数据读取与用户现有默认行为。

**Non-Goals:** 带宽最低保证、按时段变化的带宽策略和带宽优先级。

## Decisions

### 1. 状态与职责

task 持有独立 bucket，AddOptions/Item/Record 增加 TaskRateLimit，默认零；任务修改 API 同步更新持久字段并唤醒等待者。UI 沿用现有 KB/s 换算与最大 1 GiB/s 上限校验，不把限速状态放进视图局部变量。

### 2. 核心执行方式

将全局与任务许可获取封装为统一 acquireReadBudget：按固定锁序检查并同时扣减两桶，任意不足时释放两锁并等待其 changed/计时器/context，不先占用全局额度长期等任务桶。相较串行 take，避免低速任务截留全局预算；实际 read 后按未使用字节双向返还。

### 3. 一致性与边界

许可块不超过 16 KiB，桶容量沿用 rate/10 与 16 KiB 的较小值；低速时最小一字节。允许每桶容量及一个在途块的短突发，测试窗口至少数秒并将调度误差与额度边界分开断言。

### 4. 生命周期与交互

保持现有网络停滞计时范围，获取额度与磁盘写入都在计时之外；不持 Manager.mu 等待额度。任务取消要唤醒两层等待，修改限速不创建新连接；后续分片共享同一个 task bucket。

## Risks / Trade-offs

- 双桶锁顺序导致死锁或额外扣费 → 统一许可抽象、固定顺序与短读退款测试，race 覆盖更新/取消。
- 真实时间测速易抖动 → 用确定性额度测试加宽容的本地集成测量，不以外站速度验收。

## Migration Plan

新增字段默认为零，旧任务行为不变；回滚后单任务上限失效但全局上限仍生效，需在发布说明中明确。

先执行针对性用例，再执行全量测试与 MyGo 静态检查；界面变化检查两套主题、960×640 和 125% 缩放。平台服务以 deps 替身测试，原生行为另记真实验证范围。发布后更新 README 与 roadmap；本提案阶段不变更应用版本。
